# Database Migrations

This document describes the Alembic migration scaffold and path for NK HistoryGuide. Local demos default to SQLAlchemy `create_all`; staging/production-like deployments must select `HISTORYGUIDE_SCHEMA_MODE=migrated` after migrating. In that mode application startup verifies the Alembic head and model schema and does not create missing tables.

## Current Boundary

Current verified runtime path:

- SQLite
- SQLAlchemy models
- `Base.metadata.create_all` during local app startup
- fixture-based local demos

For shared deployments, `scripts/validate_runtime_config.py --profile staging` (or `production`) rejects the default `auto_create` mode. If the database lacks `alembic_version` or differs from the migration head, `migrated` startup fails rather than silently repairing it. Do not switch the live service to this mode before staging migration, backup/restore rehearsal and a planned cutover.

## Initial Migration

The initial migration creates:

- `exhibits`
- `visitor_states`
- `visitor_visit_events`

It also creates indexes used by the current SQLAlchemy models for exhibit lookup, visitor-state lookup, and visit-event timeline lookup.

The second migration creates:

- `audit_logs`

It also creates indexes for audit action, actor, resource type, and resource id filters.

The third migration creates reviewed evidence sources, exhibit/source links, and exhibit approvals. The fourth adds snapshot-bound exhibit answer runs. The fifth adds approved-source runs for general history questions. The sixth adds revocable visitor grants. The seventh stores a source approval fingerprint over ID, title, URI, and content hash. It deliberately leaves existing approved rows without a fingerprint; they fail the publication gate until a curator rechecks the original and reapproves them. These migrations define the local schema; they are not evidence that a remote staging or production database has been migrated.

## Install Dependencies

```powershell
python -m pip install -r requirements-dev.txt
```

`requirements.txt` includes Alembic so production-style environments can run migration commands after installing runtime dependencies.

## Local Migration Commands

Inspect current migration state:

```powershell
alembic current
```

Apply migrations to the configured database:

```powershell
alembic upgrade head
```

Create a future autogenerated migration after model changes:

```powershell
alembic revision --autogenerate -m "describe schema change"
```

Review autogenerated migrations manually before applying them. Autogeneration is a helper, not a substitute for schema review.

## Isolated Migration Rehearsal

Run the migration rehearsal before staging work or after editing migration files:

```powershell
python scripts\rehearse_migrations.py
```

The rehearsal runs `alembic upgrade head` against an isolated temporary SQLite database, verifies the current Alembic revision, and checks these core tables:

- `alembic_version`
- `exhibits`
- `visitor_states`
- `visitor_visit_events`
- `audit_logs`
- `evidence_sources`
- `exhibit_evidence_links`
- `exhibit_approvals`
- `review_runs`
- `history_review_runs`

The rehearsal removes the temporary database by default. Use `--keep-database` only when an operator needs to inspect the isolated SQLite file manually.

This rehearsal does not modify the configured application database, does not import records, does not validate real museum data, does not prove historical accuracy, and does not make PostgreSQL production-ready.

## Unversioned Legacy SQLite

The local MVP startup calls `create_all`. An existing SQLite database may therefore have application tables but no `alembic_version` table. **Do not run `alembic upgrade head` or `alembic stamp head` on such a database by guesswork.** A table-name match alone is insufficient.

First run the read-only-source adoption rehearsal:

```powershell
python scripts/rehearse_legacy_adoption.py PATH_TO_EXISTING_SQLITE_DB
```

The script uses SQLite's backup API to make a temporary copy, compares its tables, columns, defaults, indexes, foreign keys and constraints to each known migration revision, checks database integrity, stamps/upgrades **only the copy**, and verifies that every preexisting table's row digest is unchanged. It rejects an ambiguous or drifted schema. The source database is opened read-only and is never stamped or migrated.

The local workspace `historyguide.db` matched revision `0005_history_review_runs` in this rehearsal, preserving 9 tables and 42 rows on the copy. That says nothing about the current server database. Before any real migration adoption, identify the running build and exact target database, take and verify a restorable backup, rehearse on a staging copy of that target, and schedule a controlled cutover. A passed rehearsal does not verify museum evidence, PostgreSQL behavior, or Coze integration.

## Read-Only Staging Database Validation

After `alembic upgrade head` has been applied to a staging database, validate the live target database with read-only checks:

```powershell
python scripts\validate_staging_database.py --require-exhibits --require-sourced-exhibits --require-audit-logs
```

The validator checks:

- database connectivity
- expected core tables
- current Alembic head
- exhibit count
- empty `source_reference` values
- Visitor State count
- visit-event count
- audit-log count

It connects to the configured `HISTORYGUIDE_DATABASE_URL` or a trusted `--database-url` override. It does not run migrations, import records, write audit logs, validate historical accuracy, run RAG, or generate explanation content.

## Staging Gate

The current Alembic head includes `0008_claim_support_reviews`. This table stores operator-submitted human support decisions tied to the approved source fingerprint. It does not auto-approve existing claims or prove semantic entailment. Set `HISTORYGUIDE_CLAIM_SUPPORT_REQUIRED=true` for staging and production validation; leave it false only for isolated legacy/local tests.

After migration, run `python scripts\verify_postgres_claim_release_lock.py --acknowledge-staging-write-test` on an isolated PostgreSQL staging database. The probe intentionally creates one synthetic source and claim approval, checks multi-connection release/revocation serialization, and cleans its records by default. It refuses SQLite and must never be pointed at production.

Before using migrations in a production-like environment:

1. Export verified exhibit records.
2. Run `python scripts\rehearse_migrations.py` locally to verify the migration chain on an isolated database.
3. Apply `alembic upgrade head` to a staging database.
4. Run `python scripts\validate_staging_database.py` against the staging database to confirm schema state.
5. Import reviewed seed data into staging.
6. Run `python scripts\validate_staging_database.py --require-exhibits --require-sourced-exhibits` after import.
7. Run source and quality reports.
8. Create a test Visitor State and visit event.
9. Confirm audit logs exist for Visitor State creation and visit-event recording.
10. Run `python scripts\validate_staging_database.py --require-exhibits --require-sourced-exhibits --require-audit-logs`.
11. Check GeniOS grounding, preflight, and handoff.
12. Confirm `source_safety.ready_for_generation=true` for a sourced test session.
13. Confirm rollback steps are documented.

## PostgreSQL Boundary

Do not switch to PostgreSQL only by changing `HISTORYGUIDE_DATABASE_URL`.

PostgreSQL requires:

- a managed database or equivalent operational plan
- staging migration validation
- backup and restore validation
- source report and quality report checks after import or migration
- GeniOS handoff checks after migration
- operational monitoring

The backend still does not train models, run RAG, generate explanation content, implement digital humans, or implement AR/VR.
